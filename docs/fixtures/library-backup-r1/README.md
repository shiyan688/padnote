# Library backup r1 shared fixtures

These fixtures implement `docs/LIBRARY_BACKUP_R1_CONTRACT.md` at SHA-256 `94c283122663633026c29ac8f544f41991209914b4eefea51b6f88d82bc5a612`.

`canonical/valid-library.zip` is the cross-platform codec fixture. It contains the exact root `manifest.json` and `payload/<resource-id>.bin` members. `canonical/valid-manifest.json` is the byte-for-byte standalone manifest copy for golden parsing tests. Its manifest SHA-256 is `2d66d913ff7b5d75d5ff5101fe9a27b52b0b5018b5c595b1da8a5064dc674164`; its ZIP SHA-256 is `8f319616681acfa50abe840300c3b9040262296e69a7f0b3e693f547a5984cc5`. `canonical/fixture-pins.json` repeats those pins.

The synthetic archive covers an ordinary note, a PDF-backed note, an assigned cover, a user cover preset, an older-revision linked Vault entry, a `source_deleted` standalone Vault entry, a linked offline video, and a `source_deleted` standalone video. The linked video uses millisecond source precision (`1`); the standalone video uses second-derived milliseconds (`1000`). The original note document preserves a fractional millisecond timestamp.

All content is synthetic. Canonical note JSON now uses the app's NoteDocument fields and revision metadata, and its PDF is a valid one-page PDF. Its small MP4 entries are structural placeholders and **not playable media**; treat this ZIP as a codec fixture, not an application restore positive.

`generate-fixtures.py --output <new-directory>` creates the deterministic canonical ZIP/manifest in a directory that must not already exist. Negative ZIP conditions are created by `tools/tests/test_validate_library_backup.py`; that suite exercises Stored/Deflate, data descriptors (including manifest data) with and without signatures, deflate tails, path and reference attacks, CRC/hash corruption, truncation, ZIP64, flags and link rejection without storing misleading malformed archives as valid inputs.

`application-valid/archive/valid-library.zip` is the app-decodable positive fixture, with standalone golden `valid-manifest.json`. Its ZIP SHA-256 is `82d7bb7794e5c56d4b3ec55a498000ba6bb3e365795c467616ea553ada518abe`; manifest SHA-256 is `d895552d74c542e03c48de2f2a5b20ef17df2d39aebb0de14ea4bd8a0cdbb992`. It carries complete schema 7/8 NoteDocument payloads whose source ID/schema/revision agree with the descriptors; a PDF-backed note with matching one-page metadata; a one-page PDF; a valid 1×1 PNG; a six-second 1080×1920/30fps synthetic rendered MP4; linked historical data; and a `source_deleted` independent video entry. The MP4 is copied from the saved fake-provider E2E artifact `builtin-video-mac-e2e-root-r25-artifacts/artifacts/explanation.mp4`, SHA-256 `801cd47ebc1a1eb31c4c398374ec60fb1dc5f8dfe23665d67445a340732e6218` (264,800 bytes). The PDF comes from the repository's one-page schema7 fixture, SHA-256 `f97e1f497a1175de4389cf8b4eff4c349c848a1a92621eaee0e02649f643801d`; `pdfinfo` reports one page. Source NoteDocument templates are repository fixtures with SHA-256 `6041a5ad6604d7db7757db119c32ceb0ad0572b0176596739a70a37b96bf37a5` (schema 8) and `384ae602cb6673d3c7c4d63a795af780e73b73e1e54535989f0eafd56d26b7b9` (schema 7); the fixture generator normalizes their source IDs and timestamps to the matching manifest.

`application-valid/generate-application-fixture.py --output <new-directory>` reconstructs that app-valid archive from the checked-in source assets. It emits the iOS writer's stored UTF-8 entries with signed data descriptors, so the Python checker exercises the same member encoding and descriptor layout. The validator is still a reference checker, not a platform import/restore implementation: only the platform tests can establish that both NoteDocument/NoteStore stacks accept and restore the fixture.

The Python `tools/validate-library-backup.py` is a read-only reference checker. A successful result means the archive structure, manifest references, bounded payload lengths and hashes passed this validator. It does not implement platform import/restore, transaction recovery, or media playback.

For restored linked entries, `note_item_id` records the current copied-note association while source IDs and revisions remain historical. A linked Vault entry and a `restored_archive` video may therefore retain a source note ID different from the currently associated note; Vault descriptor and payload history must still agree. A `computer_task` video remains bound to the linked note's source ID.
